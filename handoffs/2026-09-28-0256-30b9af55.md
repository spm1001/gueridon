### Reflection
The best catch of the night came from a question I asked at deploy time, not while building: "what will the phone actually do with this?" A jsdom test of the page, an HTTP test of the endpoint and a desktop-Chrome measurement all ran green, and none of them runs a service worker. The phone does run one. The general lesson is to list what sits between the test harness and the real client (a worker, a proxy, a front door) and check each explicitly.

The essayeur split worked: one on the headline claim, one on regressions, each briefed narrowly. They found different things. A found a design choice I'd made on my own that made the worst case worse. B found a real UX regression through a scratch jsdom probe, plus four safeguards whose mutations left the tests green.

Keeping a control arm was cheap and worth it. The old page on a worktree bridge took 8.96 s against the new page's 0.25 s, which shows the instrument can see a slow page as well as a fast one.

### Risks
- **Rolling back the server without the page.** If someone rolls back to 9e51702 while a phone has the new page open, the page retries `/sessions/events` (404 on the old bridge) at 10 s, then 20, 40 … up to 5 min, while the 20 s poll keeps the roster honest. That is no worse than before. It matters only if the atelier's front door buffers; the chat view's SSE works through it, so probably not.

## For Claudes to come

**Any new streaming endpoint must go on `sw.js`'s bypass list.** The worker `index.html` registers controls every page on the origin, the launcher included. Anything not on its list takes the shell branch, which caches OK responses, and `cache.put` on an SSE stream never completes. The list is exact-match, so `/sessions` did not cover `/sessions/events`. Neither jsdom nor the HTTP integration harness runs a worker, so only reading `sw.js` (or `client/sw.test.ts`) catches this.

**To time a UI chip end to end, put every stamp on one clock.** passe's `:9223` Chrome runs on tube, so a page-side `Date.now()` from a MutationObserver shares a clock with CC's `statusUpdatedAt`. Keep the whole measurement inside one `passe run` (a long `wait` step) so device emulation holds, and raise the dialog from outside with hublot. Run a control arm on the pre-change commit via `git worktree` and a second dev bridge. `understanding.md` has the recipe under "Timing a chip end to end on one clock".

**A doorbell stream should not slow the fallback poll.** It was tempting to relax the poll while the stream was up. But a stream can die without an error (the watchdog notices after 65 s), and then the relaxed poll makes the page worse than the one it replaced. Keep the fallback at the cadence users already accepted, and let the stream only ever make things faster.
