## For Claudes to come

**Drive the real surfaces, judge by a structured witness, and watch the invariant continuously.** Guéridon's rig works because of five choices that apply beyond Guéridon. (1) Each surface is driven through its own real input path: DOM verbs in a real Chrome for the phone, keystrokes in a real TUI for the terminal, never the backend API. (2) Pass/fail comes from structured state the system writes about itself, not from screens: Claude Code's session registry (`~/.claude/sessions/<pid>.json`, with status idle/busy/waiting/shell and the tmux pane) and the transcript's `entrypoint` sequence. (3) An invariant watchdog runs alongside the scenarios (here, two live claudes on one conversation id), so a violation lasting only a moment is still caught. (4) Isolation is by construction: a private instance with its own state dir, a scratch folder, and rows picked by id. (5) Each instrument's quirks are handled once, inside its verbs. For passe: step lines on stderr, `True`/`False` results, a 15 s eval cap, and no `requestAnimationFrame` in background tabs. For the TUI: a first Enter that can be swallowed, the trust dialog, and `shell` as a prompt status.

The code is Guéridon-specific. The reusable part is a registry-backed claude-in-tmux driver (tp-gehafa) plus the passe fixes (passe-mubaji). Extract a shared library only when a second rig wants it, not before.

Separately: Claude Code's output shapes drift between versions. On 2.1.285 local-command output moved from a user line to a `system`/`local_command` line and a `<synthetic>` assistant event, and Guéridon silently showed nothing. A rig that exercises every input form is the cheapest detector of that drift.
