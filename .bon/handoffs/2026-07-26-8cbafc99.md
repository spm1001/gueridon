## For Claudes to come

**A permissive-looking wildcard in an allowlist can be silently dead, and a working neighbour masks it.** Guéridon passed `mcp__*` in `--allowed-tools` for months; CC rejects that form outright (allow globs are only valid after a literal `mcp__<server>__` prefix — deny/ask rules accept wildcards anywhere, allow rules never bare). Nobody noticed because mise kept working — via a *different, correctly-named rule* in the user's own settings.json — so "MCP works on the phone" looked true while every server without a backup rule (sonnette) was silently denied. Two generalisations. First: when an allowlist mixes rule sources, the test that means anything is the entry with **no backup rule** — the covered entry proves the backup, not the allowlist. Second: **a version bump can remove your only diagnostic** — CC v2.1.195 warned `Ignoring --allowedTools rule mcp__*` on stderr; v2.1.220 ignores it silently, so the misconfiguration became strictly harder to detect while behaving identically. Anchor done-criteria on behaviour (a matched-pair probe: real spawn, before/after, findings written to a file the orchestrator reads back), not on the presence or absence of a warning string. And derive names from the registry instead of hardcoding them: the sonnette denial existed *because* a hand-written rule carried a server name that had since drifted (`conductor-channel` → `plugin_sonnette_sonnette`) — the same drift that motivates `readPluginMcpAllowRules` reading `installed_plugins.json` fresh at every spawn.
